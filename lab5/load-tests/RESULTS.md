Дата прогона: 14.11.2026. Инструмент: k6 v1.4.2. Сценарии и запуск описаны в [README.md](README.md).

| Параметр | Значение |
| --- | --- |
| Хост | MacBook, 12 CPU, 16 ГБ RAM; во время тестов работали браузер и другие приложения (load average 5–7) |
| Docker | OrbStack VM: 12 vCPU, лимит 8 ГБ; лимитов CPU/памяти на контейнеры нет |
| Стек | docker compose: gateway (Hono + Hive Gateway), geo, seismic ×2, hazards, ops, Postgres 17, Jaeger, Prometheus, Grafana, web (TanStack Start SSR) |

| Клиенты | каждый VU — отдельный клиент (свой `X-Real-IP`) |

## Узкие места

1. **Дашборд не кешировался ни на одном уровне, и каждый просмотр запускал 4 полных агрегата по таблице
   землетрясений.** Документ `Dashboard` запрашивает `dataSources`, а для него в шлюзе задан
   `ttlPerSchemaCoordinate: Query.dataSources = 0`. Из-за этого шлюз не кеширует весь ответ
   (`responseCache: { hit: false, didCache: false }` при любом числе повторов). В итоге каждый просмотр
   главной страницы (и автообновление раз в 60 с в каждой открытой вкладке) выполнял в Postgres
   `earthquakeStats` без фильтра (31 мс, sort spill на диск 3 МБ из-за `array_agg(... order by magnitude)`),
   `earthquakeTimeline` (14 мс), `magnitudeHistogram` (12 мс) и `topSeismicCountries` (11 мс). Это четыре
   последовательных скана 59 тыс. строк. По `pg_stat_statements` эти запросы были в топе по суммарному
   времени: 173 вызова каждого за прогон `load`, 11,7 с времени БД. В прогоне на перегруженном хосте среднее
   время самого тяжёлого из них выросло до 78 мс, максимум — до 673 мс.
2. **Шлюз — однопоточный Node-процесс, и он насыщается первым.** На 50 VU (около 72 rps в среднем) он
   занимает 107–113 % CPU, то есть одно ядро плюс фоновые потоки GC и OTel. Subgraph-и и Postgres при этом
   загружены меньше чем на ядро. p95 субграфов по Prometheus около 0,2 с, а p95 ответов из кеша шлюза — 260 мс:
   запросы ждут в очереди event loop шлюза. Отказов 503 не было (in-flight ≤ 16 при лимите 200).
3. **Demand control недооценивает вложенные списки, которые пересекают границу subgraph-а.** Запрос
   `countries(limit: 249) { items { earthquakes(first: 99) { nodes { id } } } }` получает оценку 351 вместо
   ~25 000: стоимость `Country.earthquakes` из subgraph-а seismic не умножается на размер родительского списка.
   Такой запрос с вложенными `country { neighbors }` вернул 230 КБ и прошёл лимит 20 000. Защита по глубине и
   алиасам срабатывает, а по стоимости федеративные запросы проходят с заниженной оценкой.
4. Дорогих некешируемых запросов в остальном UI нет. Поиск `ILIKE` использует trigram-индекс, а вместе с
   фильтром по времени — `BitmapAnd` (0,5–15 мс). Keyset-пагинация идёт по индексам. Счётчики федерации
   (`seismicStats` для N стран) батчатся одним `GROUP BY` (3,6 мс).
5. Наблюдения о среде:
   - Prometheus собирает метрики шлюза дважды, джобами `gateway` и `local` (`host.docker.internal:4000`).
     Суммы без фильтра по `job` в Grafana удваиваются.
   - Реплика seismic, которая выиграла advisory lock и собирает данные (seismic-1), после нагрузки держит
     ~780 МБ, а вторая реплика — 180 МБ.

## Исправление: кеш агрегатов в seismic (до/после)

Новый файл `services/seismic/src/aggregate-cache.ts`. В `resolvers.ts` через него теперь идут
`earthquakeStats`, `earthquakeTimeline`, `magnitudeHistogram` и `topSeismicCountries`. Это общий для процесса
memo с TTL 15 с (`AGGREGATE_CACHE_TTL_MS`, при `0` выключается) и не больше 500 ключей. Ключ состоит из имени
поля и сериализованных аргументов. Одновременные одинаковые вызовы ждут одного SQL-запроса (single-flight),
ошибки не кешируются. Данные USGS обновляются раз в 5 минут, поэтому задержка до 15 с незаметна. Агрегаты по
странам (`Country.seismicStats` через DataLoader) не изменились. `tsc --noEmit` и unit-тесты seismic проходят.

| Метрика (load, 30 VU) | До | После |
| --- | --- | --- |
| Вызовов 4 агрегатов дашборда в Postgres | 173 каждого | 11 каждого (−94 %) |
| Время БД на эти агрегаты | ≈ 11,7 с | ≈ 0,8 с |
| Пиковая загрузка Postgres | 36 % CPU | 20 % CPU |
| Dashboard p50 / p95 | 66 / 132 мс | 55 / 124 мс |
| Все запросы p95 | 80 мс | 74 мс |

На 30 VU система не была насыщена, поэтому латентность улучшилась умеренно. Главный эффект — нагрузка на
Postgres от главной страницы больше не растёт с числом пользователей: её ограничивает примерно 4 запроса на
реплику раз в 15 секунд.

## Рекомендации

1. **Сделать дашборд кешируемым на шлюзе.** Вынести `dataSources`/`totalRecords` из документа `Dashboard`
   в отдельный маленький запрос (`apps/web/src/routes/index.tsx`) или разрешить для `Query.dataSources`
   короткий TTL, например 5 с. Тогда тяжёлые агрегаты будут обслуживаться из кеша шлюза за 2–15 мс вместо
   55–125 мс.
2. **Масштабировать шлюз горизонтально.** Это первое узкое место. В Kubernetes нужно ≥ 2 реплик шлюза и HPA по
   CPU с целью около 70 % одного ядра. Учтите, что кеш ответов и счётчики rate limit сейчас в памяти процесса
   (`InMemoryLRUCache`). С несколькими репликами лимит на клиента фактически умножится на число реплик, а
   доля попаданий в кеш снизится. Для согласованности стоит вынести их в Redis.
3. **Снизить стоимость трассировки под нагрузкой.** Сейчас трассируется каждый запрос шлюза и subgraph-ов.
   Сэмплирование 5–10 % (`OTEL_TRACES_SAMPLER=parentbased_traceidratio`) заметно разгрузит CPU шлюза.
4. **Исправить оценку стоимости для федеративных вложенных списков.** Можно задать `@listSize`/`@cost` на
   полях-расширениях (`Country.earthquakes`, `Country.naturalEvents`) так, чтобы они учитывались планировщиком
   шлюза, или ограничить вложенные connection-поля внутри списков (например, `first ≤ 10` при `limit > 25`).
   Проверку стоит добавить в `protections`.
5. **Заменить `(array_agg(id order by magnitude desc))[1]` в `statsColumns`.** Сейчас это сортировка всей
   выборки со сбросом на диск (31 мс на 59 тыс. строк). Подойдёт подзапрос `order by magnitude desc limit 1`
   с тем же фильтром или `work_mem` 8–16 МБ для Postgres.
6. Убрать дублирующий scrape-джоб `local` в Prometheus (или фильтровать по `job` в дашборде) и проследить
   за памятью реплики-сборщика seismic. В Kubernetes задать `resources.limits.memory` и
   `NODE_OPTIONS=--max-old-space-size`.
7. Шлюз и web в текущих контейнерах собраны до коммита `23302d3`. В исходниках шлюз уже доверяет `X-Real-IP`
   только вместе с `X-Internal-Token`, а SSR-прокси передаёт реальный IP клиента. После
   `docker compose up -d --build gateway web` скрипты продолжат работать: они отправляют dev-токен
   (`INTERNAL_TOKEN`). В Kubernetes токен нужно передать из секрета.

## Как повторить

```bash
./load-tests/run.sh smoke && ./load-tests/run.sh protections && ./load-tests/run.sh web
./load-tests/run.sh load      # шлюз автоматически перезапускается с поднятыми лимитами и возвращается обратно
./load-tests/run.sh stress
```

Артефакты (`results/*.json`, `*.log`, `*-docker-stats.tsv`) в git не попадают.
